## Task 2 — Interrogating "State"

The brief asks whether "State Is Not Knowledge" survives, or whether a more
precise pair of terms exists. Testing the candidate list:

| Candidate "state" | Is it a snapshot (overwrite-in-place) or a history (append-only)? | Does it already encode temporal validity? |
|---|---|---|
| Current application state | Snapshot | No |
| Database state (live tables) | Snapshot, unless the schema is explicitly bitemporal | No, unless designed in |
| Model artifact state (weights) | Snapshot per version; version history is append-only if a registry is used | No native validity interval — a registry records *when registered*, not *when this version was the one authorized for use in decision class X* |
| Configuration state | Snapshot, almost always | No |
| Repository state (git) | History (commit log is append-only) | Records *authorship/commit time*, not *when a given commit was the operative one for a specific decision* |
| Deployment state | Snapshot of "current," history if deployment records are retained | Rarely |
| Event history (event-sourced log) | History, by construction | Records event timestamps, not independently-modeled valid-time |
| Logs | History (append-only, in principle) | No — timestamps only, no valid-time/transaction-time distinction |
| Traces (OpenTelemetry) | History, but usually short-retention | No |
| Provenance records (W3C PROV) | History | Point-in-time only (generation/usage/invalidation instants) — no valid-time interval, see Objection 1 below |
| Immutable attestations (in-toto/SLSA) | History, cryptographically append-only via transparency log | Existence-before-time only (Rekor), not validity-interval |
| Audit records (NIST-style, EU AI Act Art. 12) | History | Records *when logged*, and whatever fields the schema mandates — not, by default, policy-validity-interval |

**Finding:** The "state vs. knowledge" dichotomy, as literally stated, is
imprecise for a specific and checkable reason: **several of the items Source
A implicitly treats as "mere state" are already historical, append-only
records** (logs, traces, provenance graphs, attestations, audit records) —
these are not "current state" in any meaningful sense; they already preserve
*something* about the past. Conflating them with snapshot state (a database
row, a config value) understates what ordinary engineering practice already
retains.

The real fault line is not **state vs. knowledge** but two narrower,
technically checkable distinctions:

1. **Snapshot state vs. historical record** — whether a store retains only
   the current value or an append-only sequence of past values. This
   distinction is real, well-understood, and already solved by mature
   mechanisms (version control, event sourcing, WAL-based point-in-time
   recovery) wherever it is deliberately engineered.
2. **Historical record vs. temporally-bound justificatory record** — even a
   full historical record (a complete PROV graph, a complete trace, a
   complete audit log) does not, by default, encode **which version of a
   separately-evolving dependency (policy, evidence corpus, authority
   assignment) was the operative one for a specific decision**, nor does it
   encode the **normative judgment** that made the decision valid given that
   binding. This second distinction is the one this contribution actually
   needs, and it survives even after granting that historical records are
   abundant.

**Recommended replacement formulation** (developed fully in
`novelty-verdict.md`): retire "State Is Not Knowledge" as the technical
thesis statement (retain it only as practitioner-register framing, exactly
as `claim-graph.md`'s C6 entry already flagged under its own "precision
concern"). Replace with: **retained historical state does not entail a
recorded decision-time binding to the temporally valid versions of the
policy, evidence, and authority that applied** — "state" is not the missing
half; **binding** is.

**Explicit statement, mirroring `novelty-audit.md`'s own convention:** no
single mechanism in this matrix implements the full A–G decomposition for
AI-mediated decisions under any common vocabulary. **Bitemporal databases
already solve D and E completely, in theory, wherever applied.** **in-toto +
Sigstore already solve the durable-signed-container half of a decision
record.** **W3C PROV already solves the relational/lineage representation of
evidence and authority, once populated.** None of the three is, by default,
applied to the AI-specific set of transient dependencies (prompts, live
retrieval corpora, policy-as-config, delegated agent authority), and no
existing named artifact combines bitemporal validity + structured signed
evidence + an explicit per-decision binding into one pattern for this
purpose.
