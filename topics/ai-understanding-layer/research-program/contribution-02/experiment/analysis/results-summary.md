Per `validity-and-confounders.md`, Regime A must perform measurably worse
than both B and C on the forward-drift cases (2, 4, 6, 7) or the case

| AIA | 0.60 | 1.00 | 1.00 |
| TC | 0.60 (0 on 2,4; 1 on 6,7) | 1.00 | 1.00 |

**Check passes.** A is uniformly, substantially worse than B and C on AC
and AIA across all four forward-drift cases, and specifically worse on TC
on the two cases where policy/authority themselves drift (2, 4) — TC is,
correctly, unaffected by evidence/watchlist/model drift alone (6, 7),
since TC is scoped to policy+authority identification only
(`metrics-and-scoring.md`). The case matrix has genuine drift bite.

**Documented, non-hypothesis-affecting property of Regime A:** AC is 0 in
*every* case for Regime A, including the no-drift control (Case 1). This
is architectural, not a drift-sensitivity failure: Regime A never retains
any per-decision evidence (`preservation-regimes.md`: "a single
decision-outcome log entry... nothing else"), so Question 7 is
`UNDETERMINED` by construction in every case
(`reconstruction-task.md`/`implementation-spec.md` Section 5). This is why
AC alone is not used as manipulation-check evidence above; TC and AIA are.

## Primary comparison — B vs. C

**Cases 1, 2, 4, 5, 6, 7 (control + forward-drift): B ≈ C exactly.**
TC = 1.00 and FHC = 0.00 for both regimes on all six cases. Bitemporal
history alone, competently queried, fully suffices when drift is forward
and non-retroactive — exactly what the design predicted these six cases
would show, and exactly the pattern that would let a skeptical reader rule
out "B is just weak" as an explanation for any gap seen elsewhere.

**Cases 3, 8, 9 (retroactive-drift, combined-drift): C strictly
dominates B.** TC: B = 0.00 / C = 1.00 on all three. FHC: B = 0.50 (Case
3), 1.00 (Case 8), 0.50 (Case 9) / C = 0.00 on all three. This is not a
marginal difference — it is a categorical flip on the primary metric,
concentrated exactly where the theorized mechanism (transaction-time vs.
valid-time confound under retroactive correction) predicts it.

**Case 10 (concurrency): B ≈ C, both succeed.** This does *not* match the
row-1 pattern's prediction that C should also dominate here. See
"Case 10" below — this is a disclosed consequence of an explicit,
pre-registered-as-open implementation choice, not a surprise discovered
after the fact.

## Failure taxonomy — every B failure, classified

| Case | B failure? | Classification | Root cause |
|---|---|---|---|
| 3 | Yes (TC=0) | Conflicting valid-time / transaction-time interpretation | Missing binding: nothing pins D3 to policy v1 at t0, so a later backdated correction silently changes what an as-of-t0 query returns |
| 8 | Yes (TC=0) | Conflicting valid-time / transaction-time interpretation, on *two* dimensions (policy and authority) simultaneously | Missing binding on both dimensions |
| 9 | Yes (TC=0) | Conflicting valid-time / transaction-time interpretation, on the policy dimension only (authority, model, and watchlist forward-drift dimensions all resolve correctly) | Missing binding, isolated to the one dimension that was retroactively corrected |

No B failure in this run is attributable to "insufficient underlying
evidence" or a "reconstruction-algorithm limitation": Regime B's queries
use the objectively correct bitemporal semantics
(`validity-and-confounders.md`'s internal-validity requirement), and its
full history genuinely contains the data — the query is simply, and by
design, misled by data that itself asserts something false about the
past. This is the specific, narrow failure mode the thesis names, not a
generic "B has less data" artifact.

## Case 10 — what actually happened, and why it does not match the a priori forecast

`perturbation-matrix.md` forecast that Regime B "is expected to risk
misattribution" near the policy validity boundary. `implementation-spec.md`
Section 5 explicitly leaves open whether this should be built as a genuine
fault-injection case (simulating clock/logging imprecision) or as a
documented limitation using exact interval semantics. This implementation
took the latter branch, disclosed in `PRE-EXECUTION-MANIFEST.md` before
execution: D10x's t0 (11:59) and D10y's t0 (12:01) are recorded with
minute-level precision on either side of an exact policy-boundary instant
(12:00:00), so the half-open interval query `[valid_from, valid_to)`
attributes each decision to the correct policy version unambiguously —
there is no genuine ambiguity for Regime B to fail on.

This means Case 10, as implemented, does not test the concurrency-ambiguity
mechanism `preservation-regimes.md` names as the second (distinct from
retroactive correction) reason bitemporal inference can fail. It is not
evidence that the mechanism is false — it was never actually exercised.
A genuine test would require injecting timestamp/clock imprecision (e.g.,
decision timestamps recorded with only minute or coarser granularity, or
a policy transition landing inside that granularity's uncertainty window)
so that Regime B's as-of-timestamp query has a real chance of resolving
to the wrong side of the boundary. This is a disclosed limitation of this
run, not a result.
