## Article 1 Novelty, Prior-Art, and Positioning Audit

Scope: this audit tests `draft-v2.md` (the locked editorial draft) against real prior art before an O'Reilly-ready version is produced. It does not modify `draft-v2.md`, does not touch Articles 2 or 3, and is deliberately adversarial — the goal is to find the narrowest defensible claim, not to protect the article's current framing. All sources below were retrieved via live web search on 2026-08-21 and are primary specifications, official documentation, or peer-reviewed/preprint papers where available.

## Task D — Collision test

### Objection 1 — "This is just policy-as-code" (OPA/Rego)

- **Strongest version:** OPA/Rego already lets structured input be evaluated against declarative rules to produce a decision; this is exactly what the article's "gate" does, using different words.
- **Genuinely shared:** the core mechanism — declarative rules evaluated against structured input to produce a decision — is the same in spirit as a Rego evaluation.
- **Genuine difference:** OPA is a general-purpose evaluation engine with no native domain vocabulary for AI production decisions, no native authority concept, and no native 3-way outcome type — all of that would be built by the integrator, which is exactly what the article is proposing to build.
- **Conclusion: objection substantially succeeds as a mechanism-level claim, survives only as an application-level claim.** The article should read as "here is a pattern you could implement with something like OPA/Rego as the gate," never as a competing engine.
- **Wording fix:** never imply a new policy-evaluation technology is being introduced; if a specific technology is named at all, name OPA/Rego (or an equivalent) as one way to build the gate.

### Objection 2 — "This is just a deployment gate" (GitHub Actions protection rules)

- **Strongest version:** GitHub Actions already has required reviewers, wait timers, branch restrictions, and extensible custom protection rules — exactly "evaluate conditions before a state transition, block/allow/require approval."
- **Genuinely shared:** the enforcement-point-in-pipeline concept, and human approval as a formal gate state rather than an informal exception.
- **Genuine difference:** shipped deployment gates are mostly authorization/scheduling gates (who/when/which branch), not evidence-adequacy gates — they don't natively evaluate a structured evidence bundle against declared per-decision requirements. A custom protection rule *could* call out to a service that does this, but that service is what the article describes.
- **Conclusion: survives, narrowly.** The article should be read as "what to build using a deployment gate as the mounting point," never as if deployment gates already evaluate evidence adequacy out of the box.
- **Wording fix:** the current draft's phrasing ("CI/CD is a natural fit... it already mediates the transition") is already correctly scoped; do not strengthen it to imply CI/CD platforms do the evidence evaluation themselves.

### Objection 3 — "This is just authorization" (XACML/Cedar)

- **Strongest version:** XACML's PEP/PDP/PIP/PAP model and Cedar's principal/action/resource/context model already formalize evidence (attributes/context), requirements (policy), authority (principal permissions), and a gate (PDP), with typed outcomes.
- **Genuinely shared:** this is the closest and strongest structural match of all six objections — nearly a direct correspondence.
- **Genuine difference:** XACML/Cedar decide "is principal X permitted to perform action Y on resource Z" (an access-request question); the article's pattern decides "should proposed transition D take effect" (a readiness/promotion question) — a related but distinct object of control. XACML's "Indeterminate" is an error state (evaluation failed or attributes missing), not an intentional human-escalation path, which is a real semantic difference from ESCALATE.
- **Conclusion: objection substantially succeeds.** The article should never claim to have invented an authorization model.
- **Wording fix:** if authorization terminology is used at all, it should be presented as applying well-known authorization logic to a different object (production decisions rather than access requests), not as new authorization theory.

### Objection 4 — "This is just model governance" (MLflow/Databricks/Vertex registries)

- **Strongest version:** model registries already provide staged promotion, aliases, approval tasks, RBAC-authorized promotion, and an audit trail — functionally very close to the whole pattern, for exactly the running example used in the article.
- **Genuinely shared:** the running example (promote model vN) is close to literally what these registries already do end to end.
- **Genuine difference:** registries provide the state machine and audit trail, but evidence-adequacy checking is typically manual or bolted on externally via CI, not a native declarative construct; "decision requirements" and "evidence bundle" as named, evaluable objects are not native constructs in any of the three registries surveyed.
- **Conclusion: survives narrowly, and only for the running example.** The article should not imply this pattern is unavailable in existing tooling for model promotion specifically — it already exists in close-to-finished form there.
- **Wording fix:** if the article is extended or a technical follow-up is written, this should be disclosed explicitly; not required in the current 1,800-word practitioner piece, but a real omission worth tracking (see Task G).

### Objection 5 — "This is just provenance plus CI" (SLSA/in-toto/Sigstore)

- **Strongest version:** SLSA levels + in-toto attestations + Sigstore policy-controller already give structured, signed evidence about an artifact, policy evaluated against that evidence at an admission point, and a non-binary outcome (allow/deny/warn) — for container images, which is structurally almost the same pattern applied to a different artifact type.
- **Genuinely shared:** extremely close — arguably the single closest production-grade *implemented system* to the article's full pattern.
- **Genuine difference:** the object of control is container-image admission into a Kubernetes cluster, not an arbitrary declared production decision (model promotion, pricing change, agent action). Generalizing the pattern beyond image admission to arbitrary AI-mediated decisions is a move the article makes explicit that Sigstore's own documentation does not.
- **Conclusion: this objection is very strong and should be explicitly acknowledged as the closest real-world analogue if the article is ever challenged on novelty.**
- **Wording fix:** the practitioner piece does not need to name Sigstore, but should never claim the pattern is unprecedented; a technical follow-up or FAQ should name this lineage directly.

### Objection 6 — "ALLOW/BLOCK/ESCALATE is standard access-control logic"

- **Strongest version:** ternary-or-richer decision outcomes (Permit/Deny/Indeterminate/NotApplicable in XACML; allow/deny/warn in Sigstore; approve/reject/pending in workflow systems) are extremely well established, and current academic work on agentic-system governance (Deontic Policies / AgenticRei, IEEE 2026) is already pushing past simple permit/prohibit into obligation and dispensation semantics — meaning ALLOW/BLOCK/ESCALATE is behind the current research frontier, not ahead of it.
- **Genuinely shared:** essentially total overlap on the idea of a non-binary outcome type.
- **Genuine difference:** none of real substance.
- **Conclusion: does not survive as a novelty claim.**
- **Wording fix:** ALLOW/BLOCK/ESCALATE should be presented purely as accessible, teachable vocabulary for a practitioner audience — never as a novel decision model. The current draft already does this implicitly (it never claims the outcome model itself is new); this should stay true in any future revision.

## Task E — Determine the actual contribution

**Conclusion: Position B — New synthesis**, with a substantial secondary component of Position C (framing).

Position A (new architecture) is rejected outright: XACML's PEP/PDP/PIP/PAP model (2013, OASIS Standard) and Sigstore's policy-controller (in active production use) already implement essentially the same abstraction — structured evidence, declarative requirements, an explicit gate, and a non-binary outcome — for closely adjacent objects of control. Calling the decision layer a new architecture would not survive scrutiny from anyone familiar with access-control or supply-chain-security literature.

Position D (insufficient novelty, requires substantial repositioning) is also rejected, but only barely, and only because `draft-v2.md`'s current wording already hedges carefully — "decision layer" and "evidence-gated decision" are explicitly flagged in-article as proposed, non-established terminology, and the article never claims the pattern is unprecedented. If the article *had* claimed originality for the mechanism itself, Position D would be the correct verdict. As written, the risk is one of omission (not citing adjacent prior art) rather than overclaiming (not asserting false novelty) — see Task G.

The decision between B and C is close. Position C (established mechanisms, contribution is purely the framing/mental model) is a strong secondary read — the "output ≠ decision" distinction and the ALLOW/BLOCK/ESCALATE narrative vocabulary are genuinely the article's most original and most valuable material, and neither requires any new engineering. But the article does more than reframe: it proposes a specific, coherent four-concept decomposition (evidence / requirements / authority / gate) with a concrete, implementable outcome model and working pseudocode, generalized across artifact types and decision types in a way no single audited system does explicitly. That additional, if modest, synthesis work is enough to place the article at **Position B** rather than C alone — the composition, not just the vocabulary, is the (narrow) contribution.

## Task G — O'Reilly positioning recommendation

**Claim we CAN make:** Most production AI/ML systems let a model's output become a production action with no explicit, structural checkpoint in between; naming that checkpoint as a "decision," and building it out of evidence, requirements, authority, and a gate, is a useful, teachable architectural pattern for engineers who are not already fluent in access-control or supply-chain-security literature — even though every underlying mechanism (policy evaluation, admission control, evidence attestation, staged approval) is well established elsewhere.

**Claim we SHOULD NOT make:** That this is a new architecture, a new enforcement technology, or an unprecedented idea in AI governance. It should also not be implied that no existing tool already does something close to this — ML model registries (MLflow, Databricks Unity Catalog, Vertex AI) already implement a close relative of the running example specifically, and Sigstore's policy-controller already implements essentially the same abstraction for container images.

**Best one-sentence positioning:** *A practitioner-facing name and pattern for something access-control and supply-chain-security engineers already know how to build, applied explicitly to the moment an AI system's output becomes a production action.*

**Whether the current title still works:** Yes, with no change needed. "Model Outputs Are Not Decisions: Building Evidence-Gated AI Systems" makes no novelty claim on its face — it states a distinction and describes what the article helps the reader build, not an invention claim. It survives the audit.

**Whether "decision layer" should be retained:** Yes, retain — but only because the draft already explicitly flags it as proposed, non-established terminology at first use. That hedge is now confirmed necessary and correct by this audit, not just cautious.

**Whether "evidence-gated decision" should be retained:** Yes, retain, for the same reason and with the same hedge already in place. Do not strengthen it into an unqualified proper noun (e.g., do not capitalize into "Evidence-Gated Decision" as a branded term) in this piece.

**Whether Evidence-Gated AI should appear at all:** The full phrase "Evidence-Gated AI" does not appear in `draft-v2.md`'s body (only "evidence-gated decision" and "evidence-gated" as an adjective) — this is already correct and should stay that way. Do not introduce "Evidence-Gated AI" as a named framework/proper noun in this article; the audit found close, functioning prior art for nearly every component, which makes branding the composition as a named framework the single highest-risk move available for this piece.
